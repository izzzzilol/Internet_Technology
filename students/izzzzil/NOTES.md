# Конспект по Git и Git Flow

## 1. Основы Git

1. **Git** — распределённая система контроля версий, которая позволяет отслеживать изменения в файлах и возвращаться к предыдущим версиям проекта.

2. **Репозиторий** — хранилище проекта, содержащее файлы и историю их изменений.

3. **Рабочая директория (Working Directory)** — папка проекта, в которой выполняются изменения файлов.

4. **Индекс (Staging Area)** — промежуточная область, куда добавляются изменения перед созданием коммита. Для этого используется команда `git add`.

5. **Коммит (Commit)** — сохранённая версия изменений с сообщением о том, что было сделано. Создаётся командой `git commit`.

6. Команда `git status` показывает текущее состояние файлов и ветки.

7. Команда `git diff` позволяет посмотреть изменения, которые ещё не добавлены в индекс.

8. Команда `git log` показывает историю коммитов.

9. Команда `git push` отправляет локальные коммиты в удалённый репозиторий.

10. Команда `git pull` получает изменения из удалённого репозитория и интегрирует их в текущую ветку.

## 2. Основы Git Flow

1. **Git Flow** — модель организации работы с ветками Git, которая помогает разделять разработку, подготовку релизов и исправление ошибок.

2. `main` — основная ветка, содержащая стабильную версию проекта.

3. `develop` — ветка, в которой объединяются изменения для следующего релиза.

4. `feature/*` — временные ветки для разработки новых функций. Создаются от `develop`, после завершения объединяются обратно в `develop`.

5. `release/*` — ветки для подготовки новой версии проекта. Создаются от `develop`, после проверки объединяются в `main` и обратно в `develop`.

6. `hotfix/*` — ветки для срочного исправления ошибок в стабильной версии. Создаются от `main`, после исправления объединяются в `main` и `develop`.

7. **Pull Request (PR)** — запрос на слияние изменений из одной ветки в другую. Позволяет проверить код перед объединением.

8. **Merge** — операция объединения изменений из разных веток.

9. **Merge conflict (конфликт слияния)** — ситуация, когда Git не может автоматически объединить изменения. Конфликт необходимо разрешить вручную.

10. Не рекомендуется напрямую вносить изменения в `main` и `develop`. Для работы следует создавать временные ветки.

## 3. Таблица веток Git Flow

| Ветка | Откуда создаётся | Куда сливается | Назначение |
|---|---|---|---|
| main | Начальная основная ветка | — | Стабильная версия проекта |
| develop | main | — | Интеграция изменений |
| feature/* | develop | develop | Разработка новых функций |
| release/* | develop | main и develop | Подготовка релиза |
| hotfix/* | main | main и develop | Срочное исправление ошибок |

## 4. Полезные команды Git

```bash
git init
git clone <url>
git status
git add .
git commit -m "Описание изменений"
git branch
git switch <название-ветки>
git switch -c <название-ветки>
git pull
git push
git merge <название-ветки>
git log --oneline --graph --all
git diff

## 5. Правила работы с Git Flow

1. Перед началом новой задачи необходимо обновить локальную ветку develop.
2. Каждая новая функция разрабатывается в отдельной feature-ветке.
3. Названия веток должны отражать содержание задачи.
4. После завершения разработки создаётся Pull Request в develop.
5. Перед слиянием необходимо проверить изменения и разрешить возможные конфликты.
6. Прямые коммиты в main и develop не рекомендуются.
7. После завершения релиза изменения должны присутствовать в main и develop.
